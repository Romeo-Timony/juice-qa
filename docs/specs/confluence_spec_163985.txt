Бизнес-контекст и User Story User Story: Как зарегистрированный или новый клиент веб-магазина Juice Shop, Я хочу иметь возможность безопасно регистрироваться, входить в систему, управлять персональными данными (адреса, платежные реквизиты) и восстанавливать пароль, Чтобы совершать покупки от своего имени, отслеживать историю заказов и сохранять персональные настройки безопасности. Бизнес-правила (Business Rules): BR-AUTH-01: Email пользователя должен быть уникальным в системе (case-insensitive). BR-AUTH-02: Пароль должен содержать минимум 5 символов. Поддерживается отображение индикатора стойкости пароля. BR-AUTH-03: Для сброса пароля пользователь обязан предоставить ответ на заранее выбранный контрольный вопрос. BR-AUTH-04: При успешном входе клиенту выдается JWT-токен со сроком действия, используемый для авторизации API-запросов. 3. Системный анализ и архитектурные решения 3.1. Frontend компоненты (Angular): RegisterComponent ( /#/register ) &mdash; форма регистрации нового пользователя. LoginComponent ( /#/login ) &mdash; форма аутентификации. ForgotPasswordComponent ( /#/forgot-password ) &mdash; форма сброса пароля. UserProfileComponent ( /#/profile ) &mdash; личный кабинет, смена пароля, загрузка аватара. AddressCreateComponent , PaymentMethodComponent &mdash; управление адресной книгой и банковскими картами. 3.2. REST API эндпоинты: Метод Эндпоинт Описание Тело запроса / Ответа POST /api/Users/ Регистрация пользователя { email, password, passwordRepeat, securityQuestion, securityAnswer } POST /rest/user/login Вход в систему { email, password } ➔ { authentication: { token, bid, umail } } POST /rest/user/reset-password Сброс пароля { email, answer, newPassword, repeatNewPassword } GET / POST /api/Addresss/ Список / Добавление адресов Требует Bearer Token GET / POST /api/Cards/ Список / Добавление платежных карт Требует Bearer Token 4. Функциональные требования (FR) Регистрация: Проверка формата email по RFC 5322. Запрет отправки формы с незаполненными обязательными полями. Валидация совпадения пароля и повторного пароля. Аутентификация: Сохранение JWT токена в localStorage (ключ token ). Применение токена через HTTP-интерцептор во всех последующих защищенных запросах. Восстановление пароля: Динамическая подгрузка текста контрольного вопроса по введенному email. При неверном ответе выдача ошибки без раскрытия внутренней структуры данных. Адресная книга: Возможность добавления нескольких адресов доставки с указанием страны, ФИО получателя, мобильного телефона, индекса, адреса и города. 5. Критерии приемки (BDD / Gherkin) Scenario: Успешная регистрация нового клиента Given гость открывает страницу &quot;/#/register&quot; When заполняет email &quot;client@test.com&quot;, пароль &quot;Secret123!&quot;, подтверждение &quot;Secret123!&quot; And выбирает секретный вопрос &quot;Your eldest siblings middle name?&quot; и вводит ответ &quot;Alexander&quot; And нажимает кнопку &quot;Register&quot; Then система отображает нотификацию &quot;Registration completed successfully. You can now log in.&quot; And пользователь перенаправляется на форму &quot;/#/login&quot; Scenario: Ошибка при попытке входа с неверным паролем Given пользователь находится на &quot;/#/login&quot; When вводит валидный email и неверный пароль And нажимает &quot;Log in&quot; Then отображается сообщение &quot;Invalid email or password.&quot; And JWT-токен не сохраняется в хранилище браузера 6. Нефункциональные требования (NFR) Безопасность: Хранение паролей в хешированном виде с алгоритмом HMAC-SHA256 / bcrypt. Маскирование номеров кредитных карт (отображение только последних 4 цифр). Производительность: Время генерации JWT и ответа API входа не более 200 мс.
