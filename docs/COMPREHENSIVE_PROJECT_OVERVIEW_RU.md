## 1. Введение: Какую проблему решает проект и в чем его бизнес-ценность

### Проблема классического тестирования в современных IT-компаниях
В большинстве продуктовых компаний автоматизация тестирования страдает от трех хронических проблем:

1. **Долгий цикл создания тестов (Time-to-Market bottleneck):** От момента, когда аналитик написал задачу в **Jira**, до момента появления работающего автотеста проходит от 2 до 5 рабочих дней. Инженер вручную читает требования, пишет тест-кейсы в **TMS (Test Management System)**, согласовывает их с лидом, затем садится писать код на Python/Playwright, отлаживает локаторы и создает Pull Request.
2. **Низкое качество требований («Мусор на входе — мусор на выходе»):** Часто разработчики и тестировщики начинают работу над задачами с неполными требованиями. Нет описания негативных сценариев, граничных значений и форматов ответов API при ошибках. В итоге тесты пишутся вслепую и постоянно переделываются.
3. **«Плавающие» тесты (Flaky Tests) и потеря доверия:** Тесты, написанные на скорую руку с жесткими паузами (`time.sleep`) и плохой изоляцией данных, периодически падают в **CI/CD**. Команда перестает верить отчетам, а автоматизация превращается в обузу.

### Решение, разработанное в нашем проекте
Мы создали **автономную платформу обеспечения качества (Autonomous QA & QAOps Platform)**. Это не просто набор скриптов, а умный конвейер, который:
- Сам считывает появление задачи в Jira;
- Проверяет требования на полноту с помощью искусственного интеллекта;
- Проектирует интеллектуальные карты проверок (**MindMap**) и сценарии **BDD (Behavior-Driven Development)**;
- Синхронизирует тесты с системой управления тестированием **Qase TMS** с фильтрацией дубликатов;
- Генерирует готовый код автотестов на **Python + Playwright + Requests + Pydantic** в изолированной песочнице;
- Проводит строжайший статический аудит кода без единой возможности пропустить синтаксическую ошибку или нестабильный локатор;
- **Оставляет финальное слово за человеком:** на двух ключевых этапах система запрашивает одобрение у ведущего инженера (**HITL — Human-in-the-Loop**);
- Автоматически отправляет готовый код в репозиторий через изолированные рабочие деревья (**Git Worktrees**), запускает прогон и публикует наглядный интерактивный отчет **Allure**.

### Главные цифры и результаты
- **Время от создания задачи до работающих тестов в CI:** сократилось с 1–2 дней до **менее 3 минут**.
- **Процент плавающих тестов (Flakiness Rate):** строго **0%** благодаря детерминированной изоляции данных и полному отказу от статических пауз.
- **Сквозная прослеживаемость требований (Traceability):** **100%**. Каждый шаг автотеста математически связан с конкретным критерием приемки в документации Confluence и задаче Jira.

## 2. Объект тестирования (SUT): Архитектура и специфика OWASP Juice Shop

Чтобы платформа не выглядела «сферическим конем в вакууме», в качестве тестируемой системы (**SUT — System Under Test**) выбрано популярное в индустрии enterprise-приложение электронной коммерции — **OWASP Juice Shop**.

Это полноценный интернет-магазин с реальной клиент-серверной архитектурой:
- **Пользовательский интерфейс (Frontend):** современное одностраничное приложение (**SPA — Single Page Application**) на фреймворке **Angular 21** с библиотекой компонентов **Angular Material**. Особенности: асинхронная подгрузка данных, динамические выпадающие списки, клиентская валидация форм и перехватчики запросов (**HTTP Interceptors**), подставляющие токены авторизации.
- **Серверная часть (Backend API):** высокопроизводительный сервис на **Node.js** и **Express.js**, предоставляющий богатый **REST API** для регистрации, авторизации, работы с корзиной, заказами и платежами.
- **База данных и слой данных (Database & ORM):** реляционная база **SQLite**, управляемая через **Sequelize ORM**, а также in-memory хранилище для отзывов.
- **Авторизация и безопасность:** работа через защищенные токены **JWT (JSON Web Token)** в заголовках `Authorization: Bearer <token>`, двухфакторная аутентификация (**2FA/TOTP**) и система секретных вопросов для сброса паролей.
- **Внешние интеграции:** платежные шлюзы, загрузка файлов и уведомления.

> **Почему это идеальный полигон для демонстрации SDET-навыков?**  
> Juice Shop содержит реальные бизнес-процессы и защиту от атак (**OWASP Top 10**). Тестирование такого приложения требует работы с токенами, асинхронными событиями в браузере, сложными формами и динамическими таблицами, что на голову превосходит тривиальные «демо-сайты».

## 3. Архитектурный фундамент: Почему система разделена на два контура

Одно из ключевых архитектурных решений проекта — **строгое разделение платформы на два независимых контура**.

```
┌────────────────────────────────────────────────────────────────────────┐
│ КОНТУР 1: Облачный интегратор и оркестратор (n8n Cloud + Webhooks)    │
│  - Прием событий из Jira Cloud в реальном времени                      │
│  - Проверка жизнеспособности сервисов (Health Gate)                    │
│  - Оценка требований (DoR Gate) нейросетью Gemini Flash                │
│  - Генерация интерактивных карт проверок (Whimsical MindMap)           │
│  - Синхронизация с базой тестов Qase TMS и фильтрация дубликатов       │
│  - Оповещение инженеров через Telegram-бота (@QApower_bot)             │
│  - Узлы ожидания решения человека (HITL Wait Nodes)                    │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │ Двусторонний REST API / Опрос фоновым демоном
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│ КОНТУР 2: Локальный инженерный движок автоматизации (Python Daemon)   │
│  - Фоновый сторожевой процесс (Daemon), управляющий жизненным циклом   │
│  - Генератор шаблонов автотестов (Dynamic Test Scaffolder)             │
│  - Изолированная карантинная зона для нового кода (Review Sandbox)     │
│  - Строгий статический аудит кода (AST-парсер + линтер Ruff + Pytest)  │
│  - Безопасная работа с репозиторием через Git Worktrees                │
│  - Запуск тестов: Pytest + Playwright (браузер) + Requests (API)       │
│  - Стенд эмуляции сбоев внешних систем (WireMock Standalone)           │
│  - Автоматическая изоляция и откат данных в базе (Database Teardown)   │
└────────────────────────────────────────────────────────────────────────┘
```

### Зачем нужно такое разделение? (Архитектурное обоснование)
Если попытаться запустить весь процесс внутри одного инструмента (например, все делать в n8n или все в одном монолитном Python-скрипте), возникнут серьезные проблемы:
1. **n8n великолепен в интеграциях:** он мгновенно связывает вебхуки Jira, Telegram-ботов, облачные языковые модели и базы данных без написания лишнего шаблонного кода сетевых вызовов.
2. **Но n8n не приспособлен для тяжелой компиляции и браузеров:** запуск headless-браузеров **Playwright**, компиляция синтаксических деревьев (**AST**) и выполнение тестов внутри легковесного контейнера оркестратора привели бы к утечкам памяти и зависанию системы.
3. **Безопасность и изоляция:** сгенерированный нейросетью код **никогда не должен исполняться напрямую на боевой машине**. Он должен попадать в специальный карантин локального Python-движка, проходить статический анализ без выполнения инструкций и только после этого попадать в репозиторий.

## 4. Сквозной жизненный цикл из 8 этапов: От задачи в Jira до зеленого отчета в CI

Рассмотрим детальный путь, который проходит любая бизнес-задача на примере нашей эталонной пользовательской истории **`JS-39` («Регистрация и профиль пользователя»)** и связанных с ней технических задач:
- **`JS-40`**: Автоматизация серверных контрактов REST API;
- **`JS-41`**: Автоматизация пользовательского интерфейса (Frontend UI);
- **`JS-42`**: Сквозные пользовательские сценарии (End-to-End User Journeys).

---

### Этап 0: Предстартовая проверка жизнеспособности (Health Gate)

Перед тем как тратить дорогостоящие токены нейросети или переводить задачу в работу, система запускает процедуру **Health Gate**.

Оркестратор с таймаутом в 3 секунды опрашивает 7 критических точек инфраструктуры:
1. Тестируемый интернет-магазин **Juice Shop** (`http://localhost:3000`);
2. Облачную систему управления проектами **Jira Cloud**;
3. Систему управления тестированием **Qase TMS**;
4. Сервис нейросетевых моделей **Google Gemini API**;
5. Шлюз уведомлений **Telegram Bot API**;
6. Стенд заглушек и имитации сбоев **WireMock Standalone** (`http://localhost:8088`);
7. Реляционную базу данных проекта (**SQLite / PostgreSQL**).

**Результат:** Если хотя бы один сервис недоступен, конвейер мгновенно останавливается, оставляя в задаче Jira диагностический отчет. Это предотвращает возникновение каскадных ошибок.

---

### Этап 1: Входной фильтр качества требований (DoR Gate & INVEST)

В классическом тестировании до 40% багов в автотестах возникают из-за неполноты исходного технического задания. В нашем проекте реализован автоматический шлюз готовности требований — **DoR (Definition of Ready)**.

**Как это работает:**
1. При переводе задачи в статус *«To Do»* вебхук передает текст задачи в **LLM-агент** на базе модели **Gemini Flash**.
2. Агент оценивает постановку по классическому международному стандарту качества требований **INVEST** (независимость, ценность, оцениваемость, компактность, тестируемость), а также проверяет наличие контрактов на ошибки (формат ответов 400/409, сообщения валидации).
3. Вычисляется индекс зрелости требований от 0% до 100%.

**Правило принятия решения:**
- **Оценка $\ge 80\%$ (Accept):** Требования признаются зрелыми. Задача автоматически переводится в статус **«В работе» (In Progress)**, а в комментарии публикуется подробный DoR-отчет с разбором позитивных, негативных и граничных сценариев.
- **Оценка $< 80\%$ (Reject):** Задача блокируется. В Jira создается структурированный отчет с указанием, каких именно граничных условий не хватает аналитику. Как только автор задачи дополняет описание в комментариях, система пересчитывает дельту требований и автоматически открывает проход дальше.

---

### Этап 2: Визуальное проектирование тестов (MindMap & Whimsical)

Инженеру и команде трудно читать длинные простыни текста. Для мгновенного визуального восприятия система строит **интеллектуальную карту проверок (MindMap)** с 5 уровнями иерархии:
- **Уровень 1 (Root):** Название тестируемой функциональности.
- **Уровень 2 (Domain):** Область (например, Безопасность, Бизнес-логика, Валидация).
- **Уровень 3 (Feature):** Конкретный метод или экранная форма.
- **Уровень 4 (Test Technique):** Примененная техника тест-дизайна (**Анализ граничных значений — BVA**, **Классы эквивалентности — EP**, **Таблица переходов состояний**, **Предугадывание ошибок**, **Инъекции OWASP Top 10**).
- **Уровень 5 (Expected Result & Priority):** Ожидаемый результат и приоритет (Smoke / Critical / Normal).

Система генерирует специальную разметку, которую можно в один клик вставить в визуальный редактор **Whimsical (`Ctrl+Shift+V`)**, и прикрепляет ссылку на готовую интерактивную доску прямо в карточку Jira.

---

### Этап 3: Синхронизация с системой управления тестами (Qase TMS & BDD)

Листья построенной карты проверок мгновенно преобразуются в формализованные тест-кейсы в нотации **BDD (Behavior-Driven Development)**:
- **Given (Дано):** начальное состояние системы и предусловия;
- **When (Если):** целевое действие пользователя или запрос к API;
- **Then (То):** проверяемый результат и состояние базы данных.

Далее система связывается с системой управления тестированием **Qase TMS**:
- Создает структурированный каталог сьютов (например, сьют `#86 User Registration & Profile`);
- Применяет строгое правило **Пирамиды тестирования**: 100% серверных проверок API помечаются флагом «подлежит автоматизации» (**to-be-automated**), так как они быстрые и дешевые в поддержке; в веб-интерфейсе автоматизируются только критические пути и проверки форм, а визуальные эффекты и системные диалоги операционной системы размечаются как «ручные» (**manual**);
- Присваивает каждому кейсу постоянный уникальный идентификатор (например, `QASE-787` ... `QASE-798` для API, `QASE-811` ... `QASE-822` для UI).

---

### Этап 4: Матрица сквозной прослеживаемости (Traceability Matrix, RTM)

Для гарантии того, что ни один пункт из бизнес-требований не забыт, конвейер формирует **Матрицу прослеживаемости (RTM — Requirements Traceability Matrix)**.

В задачу Jira публикуется наглядная таблица, где по каждой строке видна неразрывная цепочка:
$$\text{Критерий приемки (AC)} \longleftrightarrow \text{Ветка MindMap} \longleftrightarrow \text{ID кейса в Qase TMS} \longleftrightarrow \text{Слой (API / UI)} \longleftrightarrow \text{Статус автоматизации}$$

Если хотя бы один критерий приемки не покрыт кейсом, система сигнализирует о пробеле в покрытии еще до того, как написана первая строчка кода.

---

### Этап 5: Первый рубеж контроля человека (Quality Gate 1 — HITL)

**Принцип проекта:** Искусственный интеллект предлагает — ведущий инженер утверждает. Никакой неконтролируемой генерации вслепую.

На 5-м этапе конвейер переходит в режим ожидания (**Wait State**):
1. В Jira публикуется интерактивная карточка: `[Этап 5 из 8] Контроль 1: Подтверждение тест-кейсов (⏳ ОЖИДАЕТ СОГЛАСОВАНИЯ QA LEAD)`.
2. В рабочий Telegram-канал лида через бота **`@QApower_bot`** приходит мгновенное уведомление с прямыми ссылками на созданные кейсы в Qase TMS.
3. Инженер открывает Qase, бегло просматривает сценарии на адекватность и отвечает коротким словом **`«ОК»`** прямо в ветку (тред) 5-го комментария в Jira.
4. Фоновый демон считывает одобрение, обновляет статус комментария на `✅ ОДОБРЕНО QA LEAD` и передает управление генератору автотестов.

### Генерация кода в изолированном карантине (Test Scaffolding)

Получив одобрение тест-дизайна, движок `scaffold_dynamic.py` генерирует промышленный код на **Python**.

Код помещается в строгую карантинную зону:
- Серверные тесты: `tests/review/backend/test_js40_api.py`
- Пользовательские тесты: `tests/review/frontend/test_js41_ui.py`

**Сгенерированный код строго следует промышленным стандартам:**
- **Паттерн AAA (Arrange — Act — Assert):** тело каждого теста разделено визуальными баннерами и обернуто в шаги Allure (`@allure.step`), что обеспечивает безупречную читаемость отчетов;
- **Паттерн Page Object Model (POM):** никаких «сырых» CSS или XPath селекторов внутри тестов. Все кнопки, поля и ожидания инкапсулированы внутри классов страниц (`pages/register_page.py`, `pages/profile_page.py`);
- **Строгая типизация ответов через Pydantic v2:** ответы API проверяются не просто на статус 200, а валидируются по строгим схемам данных;
- **Прямая связка с TMS:** каждая тестовая функция именуется по шаблону `test_tc{QASE_ID}_{описание}` и маркируется декоратором `@pytest.mark.qase(id=...)`.

### Этап 6: Двухфазный контроль качества кода (Quality Gate 2)

Перед тем как допустить сгенерированный код в основной репозиторий, он подвергается беспрецедентной двухфазной проверке.

#### Фаза 1: Детерминированный статический фильтр (Static Code Gate)
Работает полностью автономно без использования языковых моделей:
1. **Синтаксический разбор через AST (Abstract Syntax Tree):** парсер стандартной библиотеки Python строит синтаксическое дерево файла. Любая опечатка, незакрытая скобка или синтаксическая ошибка отсекаются мгновенно без исполнения кода.
2. **Проверка линтером Ruff:** блокирующие правила `E9, F63, F7, F82` проверяют отсутствие необъявленных переменных, сломанных импортов и опасных конструкций.
3. **Абсолютный запрет на нестабильные паузы:** наличие вызовов `time.sleep()` или `page.wait_for_timeout()` расценивается как критический дефект и приводит к немедленной выбраковке файла.
4. **Холостой сбор тестов (Pytest Dry-Run Collect):** в изолированном окружении без доступа к сети выполняется команда:
   ```bash
   pytest --collect-only tests/review/
   ```
   Счетчик собранных тестов должен составлять **ровно 100%**. Если тест не может инициализироваться фикстурой, он не пройдет гейт.

#### Фаза 2: Семантический аудит архитектуры (LLM Code Reviewer)
Если статический фильтр пройден на 100%, специализированный промпт проверяет архитектурную чистоту кода:
- Следование паттерну Page Object;
- Полноту проверок;
- Корректность обработки ошибок.
Формируется официальный отчет аудита `tests/review/REVIEW_REPORT.md` (типовой балл: **95–100 из 100**).

В Jira выставляется карточка согласования кода. Лид оставляет финальное **`«ОК»`** в треде комментария.

### Этап 7: Безопасная интеграция в кодовую базу (Git Worktree Promotion)

Как только код одобрен, он должен попасть в ветку проекта. В примитивных скриптах это делают через обычный `git checkout / git push`, что часто приводит к конфликтам файлов и порче локального репозитория разработчика.

В нашей платформе применен высший пилотаж работы с контролем версий — **Git Worktrees (изолированные рабочие деревья)**:
1. Фоновый демон создает изолированную рабочую директорию вне основного дерева:
   ```bash
   git worktree add -B qa/js-40 .worktrees/qa-js-40 qa/main
   ```
2. Код переносится из карантина `tests/review/` в постоянную директорию `tests/backend/`.
3. **Контроль целостности содержимого (Content Digest Guard):** вычисляется криптографический хэш (SHA-256) файлов. Если такой код уже был зафиксирован ранее, повторный коммит блокируется (принцип **идемпотентности**).
4. Создается коммит с обязательной цифровой подписью разработчика (**DCO Sign-off: `git commit -s`** в соответствии со стандартами OWASP).
5. Ветка безопасно отправляется на удаленный сервер (**GitHub / GitLab**), а временное рабочее дерево бесследно удаляется. В Jira публикуется отчет о внедрении.

---

### Этап 8: Запуск в CI/CD, генерация Allure и индекс качества релиза (RQI)

Финальный аккорд жизненного цикла:
1. Тесты запускаются в среде непрерывной интеграции (**CI/CD**). Набор из 12 глубоких тестов API отрабатывает всего за **~1.01 секунды**!
2. Генерируется интерактивный отчет **Allure Report**:
   - Каждый шаг детально развернут;
   - Прикреплены полные тела запросов и ответов, HTTP-заголовки и тайминги;
   - Для UI-тестов прикреплены скриншоты финального состояния и видеозаписи сессий браузера в формате **WebM**.
3. Специальный аналитический модуль рассчитывает интегральный **Индекс качества релиза (Release Quality Index — RQI)**:
   $$RQI = 0.2 \cdot \text{DoR} + 0.3 \cdot \text{Design} + 0.2 \cdot \text{Syntax} + 0.3 \cdot \text{PassRate} = 100\%$$
4. Задача в Jira автоматически закрывается и переходит в статус **«Автотесты пройдены»** (ID перехода `31`).
5. В Telegram отправляется победное уведомление с кликабельными ссылками на Allure, Jira, Qase и коммит в GitHub.

## 5. Управление тестовыми данными (TDM) и победа над плавающими тестами

Каждый опытный автоматизатор знает: **90% нестабильности тестов вызваны грязными данными в базе и гонками состояний**.

В проекте реализована надежная стратегия **управления тестовыми данными (Test Data Management — TDM)**, гарантирующая **0% плавающих тестов**:

### 1. Предустановленные неизменяемые персоны (Deterministic Seeded Personas)
Для тестов прав доступа и бизнес-ролей используются постоянные учетные записи со строго зафиксированным начальным балансом:
- `admin@juice-sh.op` — права администратора системы;
- `jim@juice-sh.op` — учетная запись с балансом электронного кошелька **$100.00** для позитивных проверок оформления заказа;
- `bender@juice-sh.op` — учетная запись с балансом **$0.00** для проверки блокировки покупки при нехватке средств.

### 2. Динамическая генерация уникальных сущностей (UUID Isolation)
Для любых тестов, создающих новых пользователей, адреса доставки или заказы, действует строгое правило: **никаких захардкоженных email-адресов**.
Каждый запуск генерирует уникальный идентификатор:
```python
user_email = f"test_{uuid.uuid4().hex[:8]}@juice-sh.op"
```
Это полностью исключает ошибки `409 Conflict (User already exists)` при параллельных запусках или повторных прогонах.

### 3. Автоматический откат состояния базы данных (Database Teardown Fixture)
Специальная фикстура Pytest `isolate_wallet_state` подключается напрямую к базе данных приложения SQLite:
- Перед стартом теста делает снимок состояния кошельков и записей;
- По завершении теста (даже в случае падения по таймауту) выполняет SQL-транзакцию отката, возвращая баланс тестовых аккаунтов в исходное состояние и удаляя временные строки.

### 4. Моделирование сетевых сбоев через автономный WireMock (Fault Injection)
Чтобы протестировать поведение приложения при падении внешних сервисов (например, платежного шлюза), развернут сервер заглушек **WireMock Standalone** (порт `8088`).
Он позволяет эмулировать:
- Ошибки сервера `HTTP 503 Service Unavailable`;
- Превышение лимита запросов `HTTP 429 Too Many Requests`;
- Задержки сетевого ответа в 5 секунд для проверки работы защитных таймаутов (**Circuit Breakers**).

## 6. Умная дедупликация тест-кейсов: Как мы бережем базу тестов от раздувания

Когда автотесты генерируются с участием искусственного интеллекта, возникает риск **раздувания базы тестов (Test Suite Bloat)** — создание десятка похожих кейсов с чуть-чуть разными формулировками названий.

Для решения этой задачи в модуле `scripts/qase_deduplicate_evaluator.py` разработан **4-уровневый алгоритм дедупликации**:

```
                       Кандидат на добавление тест-кейса
                                     │
                                     ▼
        ┌────────────────────────────────────────────────────────┐
        │ Уровень 1: Посимвольное совпадение нормализованных имен │ ──> ДУБЛИКАТ (Отклонен)
        └────────────────────────────┬───────────────────────────┘
                                     │ Уникален
                                     ▼
        ┌────────────────────────────────────────────────────────┐
        │ Уровень 2: Совпадение сигнатуры API                    │
        │ [Метод (POST) + Эндпоинт (/api/Users) + Бизнес-цель]   │ ──> ДУБЛИКАТ (Отклонен)
        └────────────────────────────┬───────────────────────────┘
                                     │ Уникален
                                     ▼
        ┌────────────────────────────────────────────────────────┐
        │ Уровень 3: Компонент UI + Тип валидации формы          │ ──> ДУБЛИКАТ (Отклонен)
        └────────────────────────────┬───────────────────────────┘
                                     │ Уникален
                                     ▼
        ┌────────────────────────────────────────────────────────┐
        │ Уровень 4: Семантическое сходство Жаккара (Jaccard >= 85%)│ ──> ДУБЛИКАТ (Отклонен)
        └────────────────────────────┬───────────────────────────┘
                                     │ Уникален
                                     ▼
                УСПЕШНО ДОБАВЛЕН В БАЗУ ТЕСТОВ QASE TMS
```

1. **Нормализация строк:** удаление лишних пробелов, знаков препинания и приведение к нижнему регистру;
2. **Анализ сигнатуры API:** регулярные выражения извлекают HTTP-метод (`POST`), путь (`/api/Users`) и бизнес-намерение (`user_registration_password_repeat_mismatch`). Если такой контракт уже проверяется существующим кейсом — новый отсекается;
3. **Анализ контекста интерфейса:** проверка пересечения шагов на экране регистрации;
4. **Коэффициент сходства Жаккара (Jaccard Similarity $\ge 85\%$):** математическое вычисление отношения мощности пересечения множеств токенов к их объединению:
   $$J(A, B) = \frac{|A \cap B|}{|A \cup B|}$$
   Если лексическое наполнение шагов совпадает более чем на 85%, система бракует кандидата.

Благодаря этому база тестов остается кристально чистой, компактной и информативной.

## 7. Искусственный интеллект как эксперт (LLM-as-a-Judge) и PromptOps

Мы не используем ИИ как «черный ящик, пишущий код вслепую». Мы используем архитектурный паттерн **LLM-as-a-Judge (Языковая модель в роли беспристрастного судьи)** в сочетании с культурой **PromptOps (Инженерия промптов как программного кода)**.

### Принцип «Промпты как код» (Prompt-as-Code)
- Все промпты вынесены из тела программного кода в отдельные версионируемые Markdown-файлы в каталоге `prompts/` (например, `prompts/dor_evaluation/v2.0_enterprise.md`);
- Специальный класс-реестр `PromptRegistry` управляет их загрузкой и валидацией переменных;
- **Мгновенный откат без перезапуска (Zero-Downtime Rollback):** если новая версия промпта выдает неоптимальный результат, в конфигурационном файле `.env` достаточно переключить переменную:
  ```ini
  PROMPT_VERSION_DOR_EVALUATION=v1.0_baseline
  ```
  и система мгновенно вернется к проверенной базовой версии.

### Разделение зон ответственности инструментов оценки
Частый вопрос на собеседованиях: *«Почему вы не используете DeepEval для проверки кода?»*  
Наш ответ демонстрирует глубокое понимание природы инструментов:

| Инструмент | Где применяется в проекте | Почему именно он? |
| :--- | :--- | :--- |
| **DeepEval (G-Eval)** | **Контур 2 / Seam 2 (Аудит тест-дизайна)** | Метрики обработки естественного языка: **Groundedness** (заземленность: проверяет, что в шагах нет выдумок) и **Coverage** (полнота покрытия требований). Идеально для оценки текста требований. |
| **Promptfoo** | **Офлайн-разработка и тюнинг промптов** | Локальный бенчмаркинг версий промптов перед их фиксацией в Git. |
| **Static Code Gate (AST + Ruff + Pytest)** | **Контур 2 / Seam 3 (Аудит автотестов)** | **Исходный код нельзя оценивать текстовыми метриками!** Код требует детерминированного разбора синтаксического дерева, проверки импортов и тестового сбора. |
| **Langfuse** | **Сквозная телеметрия вызовов ИИ** | Фиксация каждого обращения: затраченные токены, задержка ответа, стоимость и версионный контекст. |

## 8. Отказоустойчивость, надежность и архитектурные решения (ADR)

Надежность корпоративного уровня обеспечивается 15 зафиксированными **архитектурными решениями (Architecture Decision Records — ADR)**:

```
┌───────────┬──────────────────────────────────┬────────────────────────────────────────────────────────────┐
│ Номер     │ Название решения                 │ Суть и инженерное обоснование                              │
├───────────┼──────────────────────────────────┼────────────────────────────────────────────────────────────┤
│ DEC-001   │ Seeded Personas                  │ Фиксированные учетные записи для детерминированных тестов. │
│ DEC-002   │ Page Object Model (POM)          │ Полный запрет сырых селекторов внутри тестовых функций.   │
│ DEC-003   │ Dynamic UUID Isolation           │ Изоляция создаваемых сущностей через префиксы UUID4.       │
│ DEC-004   │ AAA Banners & Allure Steps       │ Структурирование каждого теста шагами Arrange-Act-Assert. │
│ DEC-005   │ Direct Qase ID Naming            │ Именование функций вида test_tc{ID}_{desc} для связки с TMS│
│ DEC-006   │ Anti-Flaky Zero Sleep            │ Категорический запрет time.sleep, только автоожидания.    │
│ DEC-007   │ Two-Phase Code Gate              │ 100% прохождение статического аудита до вызова ИИ.         │
│ DEC-008   │ Prompt-as-Code Registry          │ Хранение промптов в Git с версионированием через .env.     │
│ DEC-009   │ Langfuse Telemetry               │ Полный трейсинг стоимости, токенов и задержек всех LLM.   │
│ DEC-010   │ Threaded HITL Approvals          │ Одобрение строго в ветке карточки этапа в Jira.           │
│ DEC-011   │ Git Worktree Isolation           │ Изолированные деревья Git для коммитов без конфликтов.    │
│ DEC-012   │ WireMock Fault Injection         │ Эмуляция 503/429 и сетевых задержек внешних интеграций.    │
│ DEC-013   │ Pydantic Strict Typing           │ Валидация контрактов API через строгие схемы Pydantic v2.  │
│ DEC-014   │ Idempotent Transitions           │ Защита от повторных переходов задач по хэш-ключам.         │
│ DEC-015   │ Audit Trail Preservation         │ Пожизненное сохранение отчетов аудита REVIEW_REPORT.md.    │
└───────────┴──────────────────────────────────┴────────────────────────────────────────────────────────────┘
```

### Автоматический предохранитель (Circuit Breaker) и безопасные резервы (Fallbacks)
Если сторонний сервис (например, Google Gemini API) временно недоступен или исчерпал лимит запросов:
- Модуль сетевого взаимодействия делает повторные попытки с экспоненциальной задержкой (**Exponential Backoff**);
- Если сервис не отвечает, срабатывает **детерминированный резервный механизм (Deterministic Fallback)**: код анализируется эвристическим анализатором на базе регулярных выражений и структуры AST, что гарантирует: **конвейер никогда не зависнет намертво**.

### Вопрос 1: Зачем было разделять систему на два контура, вместо того чтобы сделать все внутри n8n или целиком на Python?
> **Ответ:**  
> «Это фундаментальный принцип разделения ответственности (**Separation of Concerns**). **n8n** великолепен в качестве облачного событийно-ориентированного оркестратора: он мгновенно обрабатывает вебхуки Jira, управляет телеграм-ботами и связывает внешние API.  
> Однако тяжелые инженерные задачи — запуск браузеров **Playwright**, синтаксический анализ деревьев **AST**, компиляция линтерами и работа с изолированными деревьями **Git Worktree** — требуют полноценной среды выполнения. Запуск таких процессов внутри контейнера n8n привел бы к пожиранию ресурсов и нестабильности. Поэтому n8n выполняет роль дирижера (Контур 1), а фоновый Python-демон — роль мощного изолированного исполнителя (Контур 2)».

---

### Вопрос 2: Как вы гарантируете, что языковая модель не начнет галлюцинировать и придумывать лишние или дублирующие тесты?
> **Ответ:**  
> «Защита построена на трех эшелонах:  
> Во-первых, на этапе тест-дизайна работает метрика **Groundedness (заземленность)**: каждый шаг сценария математически привязывается к конкретному критерию приемки (**Acceptance Criterion**).  
> Во-вторых, действует наш **4-уровневый движок дедупликации** в `qase_deduplicate_evaluator.py`: он сравнивает нормализованные названия, сопоставляет сигнатуры API (метод + маршрут + бизнес-цель) и вычисляет коэффициент сходства Жаккара с порогом 85%.  
> В-третьих, работает первый рубеж контроля человека (**HITL-1**): сгенерированные кейсы не идут в разработку, пока ведущий инженер лично не подтвердит их в Jira».

---

### Вопрос 3: Почему вы не используете DeepEval для проверки сгенерированного кода тестов на Python?
> **Ответ:**  
> «Потому что **DeepEval** и метрики семейства **G-Eval** созданы для анализа естественного языка — сопоставления смысла текста с текстом. Применять языковую модель для оценки исходного кода — дорого и ненадежно: нейросеть может легко пропустить пропущенную запятую или необъявленную переменную.  
> Для программного кода существует строгий детерминированный инструментарий: **AST-парсер** стандартной библиотеки Python, линтер **Ruff** (правила E9/F82) и команда холостого сбора **`pytest --collect-only`**. Только когда статический анализ подтвердил 100% валидность синтаксиса, подключается легковесный аудит архитектурных паттернов».

---

### Вопрос 4: Как решена проблема изоляции данных в базе? Что защищает тесты от взаимовлияния?
> **Ответ:**  
> «Мы применяем трехуровневую стратегию **TDM (Test Data Management)**:  
> 1) Для тестов прав доступа используются неизменяемые эталонные персоны (**Seeded Personas**): администратор и аккаунты с фиксированным балансом ($100 и $0);  
> 2) Для любых операций создания (регистрация, добавление адресов) адреса и логины генерируются динамически через **`uuid.uuid4().hex[:8]`**, что исключает конфликты уникальности;  
> 3) Специальная фикстура Pytest `isolate_wallet_state` подключается к базе данных SQLite и откатывает транзакции после завершения каждого теста».

---

### Вопрос 5: Что происходит, если ведущий инженер отклоняет тест-дизайн на первом шлюзе контроля (Quality Gate 1)?
> **Ответ:**  
> «Пайплайн безопасно встает на паузу. Задача в Jira блокируется, а инженеру или аналитику достаточно написать комментарий с уточнениями прямо в ветке обсуждения. Фоновый демон считывает это сообщение, запускает модуль `qaops_delta_refine.py`, который вычисляет разницу требований, актуализирует карту проверок и BDD-сценарии, после чего повторно запрашивает согласование. Никаких ручных перезапусков конвейера не требуется».

---

### Вопрос 6: Зачем понадобился автономный WireMock, если в Python есть стандартная библиотека `unittest.mock`?
> **Ответ:**  
> «`unittest.mock` подменяет вызовы функций в памяти внутри одного процесса Python. Он не способен проверить реальное сетевое взаимодействие, поведение HTTP-клиента, сериализацию заголовков или работу сетевых таймаутов.  
> **WireMock Standalone** работает как независимый внешний HTTP-сервер. С его помощью мы проводим полноценное стресс-тестирование (**Fault Injection**): эмулируем 5-секундные задержки сети, ответы 503 Service Unavailable и 429 Too Many Requests, проверяя, как реальный клиент Juice Shop и наши тесты справляются с сетевыми сбоями».

---

### Вопрос 7: Как предотвращаются состояния гонки (Race Conditions) при параллельном добавлении комментариев в Jira?
> **Ответ:**  
> «Благодаря архитектурному решению **DEC-010 (Threaded HITL Approvals)**. Система полностью игнорирует общие комментарии к тикету верхнего уровня и отслеживает только ответы внутри конкретного треда карточки этапа (`stage_comment.id`). Кроме того, каждый обработанный идентификатор комментария заносится в локальное хранилище с блокировками транзакций, что исключает повторное срабатывание».

---

### Вопрос 8: Как устроено версионирование промптов и как вы откатываетесь, если модель стала отвечать хуже?
> **Ответ:**  
> «По принципу **Prompt-as-Code (DEC-008)**. Промпты хранятся в репозитории как обычные Markdown-файлы с семантическим версионированием (`v1.0_baseline.md`, `v2.0_enterprise.md`). Реестр `PromptRegistry` подгружает нужный файл на основе переменной окружения `.env`. Для мгновенного отката на предыдущую версию не нужно пересобирать проект — достаточно сменить версию в конфиге, и система на лету переключится на старый проверенный промпт».

---

### Вопрос 9: Как в сгенерированных тестах соблюдается классическая Пирамида Тестирования?
> **Ответ:**  
> «На этапе форматирования тестов (`08_format_testcases.js` и `scaffold_dynamic.py`) заложено жесткое правило распределения слоев:  
> Все тесты серверных контрактов API на 100% размечаются для обязательной автоматизации, так как они работают за миллисекунды и практически не требуют затрат на поддержку.  
> Для интерфейса UI автоматизируются только критические пути (**Smoke / P1**), а второстепенные стилистические эффекты и системные окна размечаются флагом `manual`, защищая команду от хрупких и медленных UI-сьютов».

---

### Вопрос 10: Каким образом достигнут показатель Flakiness = 0% в пользовательских тестах?
> **Ответ:**  
> «Благодаря архитектурному стандарту **DEC-006**: полный отказ от жестких пауз `time.sleep()` и `wait_for_timeout()`. Это контролируется на уровне статического анализатора кода.  
> Вместо этого тесты на **Playwright** используют интеллектуальные веб-утверждения с автоматическим ожиданием (**Auto-waiting assertions**): `expect(locator).to_be_visible()`, которые ждут появления и стабильности элемента на уровне событийного цикла браузера».

---

### Вопрос 11: Почему для фиксации автотестов в Git используются Git Worktrees?
> **Ответ:**  
> «Архитектурное решение **DEC-011**. Обычные операции `git checkout` в автоматических фоновых скриптах опасны: если в локальной директории у инженера есть несохраненные изменения, переключение веток может привести к конфликтам или потере данных.  
> **Git Worktree** позволяет демону создать полностью изолированную рабочую копию в отдельной скрытой папке `.worktrees/`, перенести туда проверенный код, подписать коммит (`-s`), отправить ветку в origin и удалить рабочую папку, вообще не трогая открытый проект инженера».

---

### Вопрос 12: Что такое Индекс качества релиза (Release Quality Index, RQI) и как он рассчитывается?
> **Ответ:**  
> «**RQI** — это интегральная математическая метрика готовности функциональности к релизу, рассчитываемая модулем `qaops/metrics.py`. Она агрегирует четыре ключевых показателя с весовыми коэффициентами:  
> 1) Зрелость требований DoR ($\ge 80\%$);  
> 2) Полнота тест-дизайна ($\ge 90\%$);  
> 3) Валидность синтаксиса и сбора тестов (строго 100%);  
> 4) Процент успешного прохождения автотестов (100%).  
> Только если итоговый индекс равен 1.0 (100%), система выдает официальную рекомендацию на релиз и автоматически переводит тикет в финальный статус».

---

### Вопрос 13: Что произойдет, если у Google Gemini закончатся квоты или пропадет интернет?
> **Ответ:**  
> «Система защищена от сетевых сбоев. Все обращения обернуты в механизм повторных попыток с экспоненциальной задержкой. Если сервис недоступен длительное время, активируется **детерминированный резервный аудитор (Fallback Heuristic)**: система временно отключает семантический аудит и оценивает код по строгим структурным правилам синтаксического дерева. Пайплайн успешно завершит работу и не оставит команду без тестов».

### Вопрос 14: Как тесты в кодовой базе связаны с системой управления тестированием и отчетами?
> **Ответ:**  
> «Согласно стандарту **DEC-005**, каждая функция в коде получает строгое имя вида `test_tc{QASE_ID}_{description}` и помечается декоратором `@pytest.mark.qase(id=...)`. При запуске плагин Qase и Allure-репортер автоматически транслируют результаты прогона каждого метода в карточку соответствующего кейса в Qase TMS и строят кликабельные связи в отчете Allure».

### Вопрос 15: Почему именно OWASP Juice Shop стал идеальной демонстрационной базой для этого проекта?
> **Ответ:**  
> «Juice Shop — это признанный золотой стандарт современного веб-приложения: здесь есть и реактивный **Angular SPA**, и полноценный **REST API**, и авторизация по **JWT**, и реляционная база данных. При этом он содержит реальные вызовы безопасности: инъекции, валидацию сложных паролей, разграничение прав доступа. Построить надежную и стабильную систему автоматизации на таком комплексном проекте — лучшее подтверждение зрелости инженерных решений».

## Резюме для интервьюера: Главный вывод

Этот проект — не просто автоматизация кликов в браузере или вызовов эндпоинтов.  
Это **зрелая инженерная экосистема обеспечения качества (QA Engineering Ecosystem)**, в которой:
- Рутинная работа по чтению документации, проектированию кейсов и написанию типового кода передана проверенным алгоритмам и искусственному интеллекту;
- Человек освобожден от механической работы и выступает в роли главного эксперта-валидатора (**HITL**);
- Внедрены лучшие практики мировой программной инженерии: **AST-анализ**, **TDM с откатом транзакций**, **Git Worktrees**, **Pydantic-контракты** и **Circuit Breakers**;
- Достигнута главная цель любого бизнеса: **сокращение времени вывода фичи на рынок (Time-to-Market) с дней до считанных минут при безупречном качестве**.
